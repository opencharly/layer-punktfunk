# 2026.241.2026 — feat: enable systemd user lingering for the packaged user units

## Summary

punktfunk ships as a **systemd USER service**, and a `scope: user` unit only runs without
an interactive login if the account **lingers**. punktfunk's own always-on recipe says so
outright — *"Enable user lingering: `sudo loginctl enable-linger "$USER"`"* — and charly's
deploy path does not do it:

```
$ grep -rn 'enable-linger' --include='*.go' sdk/ spec/ charly/charly/
(no matches)
```

Without it the three packaged units install, are enabled, and never run on a headless VM.
This closes that gap, which is part of installing punktfunk correctly rather than a
bed-specific fixup.

**Capability-gated, not distro-gated.** `/run/systemd/system` is the canonical "systemd is
the running init" test, so the step no-ops during an image build and inside a supervisord
container — venues with no user units to run — instead of failing there.

The PR also carries a matching check, and corrects two checks that a real systemd guest
proved were asserting the wrong thing (second commit; details below).

## Two checks were wrong, and only the live guest showed it (R1)

The first VM run **failed**, which is why the bed earns its keep:

```
FAIL  the container-venue launcher wrapper is installed and executable  [punktfunk-wrapper-installed]  exists=false
FAIL  the punktfunk host user unit is enabled on a systemd venue        [punktfunk-user-unit-enabled]  exit=1
```

**1. `runuser -u <user> -- systemctl --user` reaches no user bus.** systemd itself names the
fix in the error text:

```
Failed to connect to user scope bus via local transport: $DBUS_SESSION_BUS_ADDRESS and
$XDG_RUNTIME_DIR not defined (consider using --machine=<user>@.host --user to connect to
bus of other user)
```

The unit was `enabled` and `active` the whole time — the *check* was broken, not the
feature. Switched to the prescribed `--machine="$PF_USER@.host" --user` form and verified
it as the unprivileged user on the live guest (`enabled`, exit 0).

**2. The wrapper check asserted an artifact with no role on that venue.** The wrapper is the
launch path **only** under a container init, because supervisord cannot use the packaged
systemd user unit. On a systemd venue the packaged unit is the launch path and the wrapper
is irrelevant, so asserting its presence there asserts nothing meaningful. The check is now
scoped to the venue the wrapper exists for and reports an explicit N/A elsewhere rather
than passing mute.

### A `copy:`-on-VM-deploy defect surfaced here — routed to a named issue

On the VM deploy the candy's `mkdir:`, `write:` and `command:` steps all applied —
`host.env` landed at `/home/arch/.config/punktfunk/host.env`, lingering was set — but the
`copy:` step did not deliver `punktfunk-host-wrapper`; `~/.local/bin/` was created and
empty. The step is **absent from the deploy plan entirely** rather than failing
(`grep -c punktfunk-host-wrapper deploy-add.log` → `0`), and `deploy-add` still reported
PASS. The same `copy:`, same file, delivers correctly on the image-build path, so it is
not source resolution.

Tracked as **opencharly/charly#460**, which carries the full measurement, the
build-vs-deploy contrast and a reproducer. It is filed rather than fixed here because the
fix is in charly's deploy lowering, not in this candy, and I have not root-caused which
stage drops the step — guessing at core deploy code from a candy PR would be worse than
naming it.

**This PR does not depend on that behaviour.** The wrapper check is venue-scoped on its own
merits: the wrapper is the launch path only under a container init, so on a systemd venue
its absence is meaningless regardless of how `copy:` behaves. Flagged prominently because
`pod-sway` delivers its `sway-wrapper` and `config` the same way, so a `target: vm` deploy
of the sway stack would land a compositor with no launcher.
