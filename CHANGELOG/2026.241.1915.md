# 2026.241.1915 — feat: punktfunk streaming host candy (Arch/CachyOS)

## Summary

First charly support for [punktfunk](https://git.unom.io/unom/punktfunk), a Rust
game/desktop-streaming **host daemon** (native `punktfunk/1` QUIC protocol, plus
Moonlight/GameStream compatibility). The org had no punktfunk surface at all, and no
game-streaming host of any kind — the existing `selkies-*` / `wayvnc` / `sway-*` corpus
streams a *desktop out of a container* over WebRTC/VNC, which is a different axis.

This candy installs the host on **Arch and CachyOS** (one `distro.arch:` section: the
cachyos base declares `distro: [cachyos, arch]`, so the cascade resolves it on both):

- Adds the `[punktfunk]` pacman repo from unom's Gitea registry and imports + locally
  signs its release key. The `Server` line carries pacman's own `$repo` / `$arch`
  placeholders — the pac install template emits it inside a single-quoted `printf`, so
  they reach `/etc/pacman.conf` verbatim for pacman to expand. `SigLevel` is
  `Required DatabaseOptional`, so package signatures are actually enforced.
- Installs `punktfunk-host`, `punktfunk-web` and `punktfunk-scripting`.
- Writes `~/.config/punktfunk/host.env` pinning `PUNKTFUNK_COMPOSITOR=wlroots`,
  `PUNKTFUNK_INPUT_BACKEND=wlr`, `PUNKTFUNK_VIDEO_SOURCE=virtual`,
  `PUNKTFUNK_ENCODER=software` and `PUNKTFUNK_ZEROCOPY=0`. Pinned rather than
  auto-detected on purpose: auto-detection picks whatever compositor is live, which would
  make a check bed's result depend on the venue instead of on the config.
- Joins the deploying user to `input` (controller support), resolving the account via
  `getent passwd 1000` because a RUN shell does not export `$USER` and the image may be
  in adopt mode.

**Two service forms, because punktfunk is a systemd USER service upstream.** The packaged
`punktfunk-host` / `punktfunk-web` / `punktfunk-scripting` units are enabled with
`scope: user` on a systemd venue. A container venue gets a charly-owned wrapper that waits
for the Wayland socket and then sway's IPC socket before exec'ing the host — punktfunk's
wlroots backend creates its virtual output by calling `swaymsg create_output`, so starting
before sway listens yields a host that runs but can never produce a display. The wrapper
also sources `host.env`, which supervisord (unlike the packaged unit) does not read.

That wrapper mirrors `pod-wayvnc`'s `wayvnc-wrapper` deliberately — same dependency, same
venue, same two-phase wait — so the repo keeps **one** readiness idiom rather than growing
a second (R3).

### One check failed first, and was root-caused rather than patched around (R1)

The initial key probe ran `pacman-key --list-keys --with-colons` and failed:

```
FAIL  the imported release key carries the published punktfunk fingerprint  exit=1
      (stderr: pacman-key: invalid option '--with-colons')
```

Root cause: `pacman-key` does its own option parsing and does not forward `--with-colons`
to gpg — it is a gpg option, not a pacman-key one. Fixed by querying gpg directly against
the pacman keyring, which is the same idiom the pac install template itself uses.

The fix also made the assertion **stronger**. The original only checked that the
fingerprint appeared; the replacement asserts `pub:f:` (full validity) for that exact
fingerprint, which a key only reaches after `pacman-key --lsign-key`. An imported but
unsigned key would still let the repo be listed while every package install failed
signature verification — so presence alone proved nothing. Verified against the live
keyring, including that the published key file carries **two** keys and the template's
`awk ... exit` signs the first, which is the documented `E0CA0446…`:

```
$ gpg --homedir /etc/pacman.d/gnupg --batch --list-keys --with-colons E0CA04465C99C936E0B0C6510A317015A34DDD69 | grep '^pub'
pub:f:2048:1:0A317015A34DDD69:1783185071:::-:::scESC::::::23::0:
```

The now-unused `var: PUNKTFUNK_KEY_FPR` was deleted in the same change rather than left
dangling (R5); the fingerprint is inlined because `var:` is a build-time ENV and would be
empty on a VM/host deploy.


### The wrapper executes — runtime proof (addressing the first review)

The first review correctly blocked this: the wrapper was a new executable whose behaviour
had never run, and the only check covering it asserted file-exists + mode. Both halves are
now fixed — the behaviour is executed below, and a check that *would fail* if it broke is
committed (`punktfunk-mgmt-api-live`, second commit).

**Negative path** — no compositor. The wrapper must refuse to start the host rather than
hang or exec blindly:

```
$ podman run --rm -u 1000 -e XDG_RUNTIME_DIR=/tmp -e WAYLAND_DISPLAY=wayland-0 <img> \
    sh -c 'time punktfunk-host-wrapper'
punktfunk-host-wrapper: Wayland socket /tmp/wayland-0 not found after 30s
real    0m30.048s
RC=1
```

**Positive path** — a real headless sway in the container, then the wrapper:

```
=== wrapper log (empty = it got past BOTH waits) ===

INFO punktfunk_host::mgmt_token: generated and persisted API token (owner-only) path=/home/user/.config/punktfunk/mgmt-token
INFO punktfunk_host::native: punktfunk/1 host listening (QUIC) port=9777 source=Virtual
INFO punktfunk_host::mgmt: management API listening over HTTPS addr=127.0.0.1:47990

HOST-EXEC-OK

=== did the wrapper export SWAYSOCK to the host? ===
SWAYSOCK=/tmp/sway-ipc.1000.3.sock
SWAYSOCK-EXPORTED-OK

=== did it source host.env? ===
PUNKTFUNK_COMPOSITOR=wlroots
PUNKTFUNK_ENCODER=software

{"status":"ok","version":"0.33.0-1","abi_version":26}
```

Every claim the wrapper makes is covered: both waits cleared, `SWAYSOCK` exported (the
load-bearing one — punktfunk drives `swaymsg create_output` through it), all four
`host.env` pins present in the host's own environment, `exec` reached, and the host
reporting `source=Virtual`, i.e. the virtual-display pin actually took effect.

Two findings came out of getting there, both fixed in the harness rather than worked around:

1. Arch's `sway` ships `cap_sys_nice=ep` and refuses to exec in a container
   (`Operation not permitted`). `pod-sway` already strips exactly this capability, so the
   spike does the same rather than inventing a second fix.
2. wlroots treats a set `WAYLAND_DISPLAY` as an upstream compositor to nest into and
   therefore skips `wayland-0`. `pod-sway`'s `sway-wrapper` documents this and symlinks the
   expected name for sibling services. **The wrapper here was correct; the first spike
   harness was not** — it started sway directly instead of honouring that contract. The
   harness now replicates it, which is also why this candy keeps the same assumption
   `pod-wayvnc` makes instead of inventing a second discovery mechanism (R3).

Note the host writes its bearer token to `~/.config/punktfunk/mgmt-token` — exactly the
path the companion `punktfunk:` verb plugin defaults its token discovery to.

## Rulebook compliance

- **R1** — the one failing check was root-caused (pacman-key's own option parsing) before
  any remediation; no "pre-existing" or "out of scope" classification.
- **R3** — the container-venue readiness wait reuses `pod-wayvnc`'s established
  wrapper idiom instead of introducing a second one; the key query uses the same gpg
  invocation the pac install template uses.
- **R4** — no hand-pinned workaround for the repo/key path: the declarative
  `distro.arch.repo:` block drives it, and the pac template's existing `--lsign-key` leg
  was verified to cover punktfunk's requirement rather than being worked around.
- **R5** — `var: PUNKTFUNK_KEY_FPR` removed in the same commit that stopped using it.
- **R6** — no force-push, no hook bypass. The pre-commit gate rejected a heredoc commit
  and the commit was redone with `-F <file>` rather than disabled.
- **R7 / R10** — the verification above was re-run from the **corrected** tree (rebuild →
  re-check), not from the edited state that produced the first failure.
- **A2 / B12** — addressed head on rather than deferred: the changed runner now executes
  live in this PR, and `punktfunk-mgmt-api-live` is a check that fails if the launch path
  breaks.
- **A1** — the footer's parenthetical is the confidence value from the rulebook's own
  attribution-tier table (`fully tested and validated`, `analysed on a live system`, …),
