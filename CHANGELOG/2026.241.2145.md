# 2026.241.2145 — feat: add the punktfunk-host skill

## Summary

Adds the `punktfunk-host` skill. Nothing in the marketplace documented the punktfunk
streaming host, so no agent could discover it from the skill corpus — the gap called out
when the candy landed.

The prose deliberately records the things that are **not** recoverable from the YAML:

- **Why two service forms exist.** punktfunk is a systemd USER service upstream and
  supervisord cannot use one, so the container venue runs a wrapper instead.
- **Why that wrapper waits for sway's IPC socket.** punktfunk creates its virtual output by
  calling `swaymsg create_output`; a host started before sway listens runs but can never
  produce a display. It mirrors `pod-wayvnc`'s wrapper so the repo keeps one readiness idiom.
- **Why lingering is part of installing it correctly**, not a bed fixup — a `scope: user`
  unit needs it, and charly's deploy path does not enable it.
- **Why `host.env` is pinned** rather than auto-detected: auto-detection makes a bed's
  result depend on the venue instead of the config.
- **That the pacman `$repo`/`$arch` variables are deliberate** (the pac template emits them
  inside a single-quoted `printf`), so nobody "fixes" them into literals.
- **That `punktfunk-host` must never be `setcap`'d** — upstream is explicit that caps
  belong on `punktfunk-encode-worker` and setcap on the host breaks KDE capture.
- **That the management-token file is an env-file line**, not a bare token — the exact trap
  that produced a clean HTTP 401 during the verb's live testing.

Family `punktfunk`, registered in opencharly/pod-charly-hooks#3; that PR must land first,
since a skill naming an undeclared family is a hard generator error.
