# 2026.242.1658 — docs(punktfunk): say that a compositor alone does not get frames out

## Summary

The description said punktfunk "creates its virtual output via `swaymsg create_output`",
which reads as though sway is the whole capture path. It is not.

A session resolves to `capture: Portal`. The host asks **xdg-desktop-portal**'s ScreenCast
interface to create the virtual output and then receives frames over **PipeWire**; the
wlroots backend drives sway underneath. From a live host's own log:

```
INFO punktfunk_host::native::stream: resolved session plan plan=SessionPlan {
     capture: Portal, topology: SingleProcess, encoder: Software, codec: H264, ... }
INFO pf_vdisplay::wlroots: pointed xdg-desktop-portal-wlr at the managed output chooser
INFO pf_vdisplay::wlroots: sway headless output ready node_id=43 output=HEADLESS-13 w=1920 h=1080
```

So a venue needs `layer-xdg-portal` and `pod-pipewire` as well as a compositor, and this
candy does not pull them in. Nothing said so.

### Why it is worth documenting rather than leaving implicit

The failure is silent in a misleading way. With no portal the host installs, its units
reach active, the management API answers, pairing succeeds and a codec is negotiated —
**every control-plane check passes** — and then every session dies at pipeline build:

```
WARN punktfunk_host::native::stream: pipeline build failed — retrying attempt=1 max=8
     error=create virtual output: ScreenCast portal on HEADLESS-2 failed: A portal
     frontend implementing `org.freedesktop.portal.ScreenCast` was not found
```

That combination — a green control plane over a host that can never send a frame — is
exactly what let a two-member fleet bed report PASS while nothing had ever streamed.

The note about `XDG_CURRENT_DESKTOP` is included because it is easy to lose: the portal
frontend selects its backend from that variable, and D-Bus activation supplies no
environment of its own. Installing the portal packages without it yields a frontend that
activates on demand while the wlr backend never does, and the interface is simply absent:

```
zbus::proxy: No such interface "org.freedesktop.portal.ScreenCast"
```

Verified directly rather than inferred — the activated frontend's own environment:

```
$ tr '\0' '\n' < /proc/5342/environ | sed -n 's/^XDG_CURRENT_DESKTOP=//p'
(empty)
```

`layer-xdg-portal` sets it, both as an image `env:` and via a sway `config.d` snippet
running `dbus-update-activation-environment`, which is why composing that candy works where
starting the portal binaries by hand did not.
